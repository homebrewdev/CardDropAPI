# MultiTool: текущие фиксы CardDrop

Дата: 2026-11-13

Документ фиксирует исправления, сделанные в проекте CardDrop:
починку сценария «второй игрок заходит в комнату», визуализацию стола
и переход на случайную раздачу из колоды сессии.

---

## 1. Второй игрок не видел комнату и игру

### Симптомы

- Первый игрок создавал комнату и видел экран ожидания.
- Второй игрок входил по коду и получал пустой экран.
- После нажатия «Начать игру» карты не появлялись ни у кого.

### Причины

1. `frontend/src/App.tsx`: `joinSession` не записывал `session`, а экран
   ожидания рендерился по условию `session && gameState`. У второго игрока
   `session` оставался `null` — экран не отрисовывался.
2. `app/rooms/room_manager.py`: метод `join()` отправлял снапшот состояния
   только вошедшему игроку. Первый игрок не узнавал о втором до следующего
   игрового события.
3. В интерфейсе не было кнопки старта партии: `handleStartRound` нигде
   не вызывался, а `GameTable` игнорировал `onReady` и `onStartRound`.
4. `_build_state()` возвращал Pydantic-модели карт. `websocket.send_json`
   вызывает `json.dumps`, который такие объекты не сериализует. Ошибка
   проглатывалась в `send_to()`, поэтому после старта состояние с картами
   не доходило ни до одного клиента.

### Что исправлено

**Бэкенд**

- `join()` после входа игрока рассылает полные персональные снапшоты всем
  в комнате (`_broadcast_states`), а не только новому игроку.
- `_build_state()` теперь отдаёт обычные JSON-словари: карты собираются
  через `PlayerCardResponse(...).model_dump()`.
- В `game_state` добавлен блок `session`: `id`, `name`, `join_code`,
  `status`, `max_players`, `current_players`. Игрок, вошедший по коду,
  не делал REST-запроса создания комнаты и иначе не знал её параметров.
- `send_to()` больше не глотает ошибки молча: пишет `warning` с типом
  сообщения и трейсбеком.
- Добавлен публичный `broadcast_states()`; после `ready` и `set_bet`
  состояние тоже рассылается, а не только событие.
- В WS-обработчике действия `ready`, `play_card`, `pass`, `fold`
  используют `player.id` из соединения, а не `player_id` из payload.
- Проверка заполненности комнаты считает реально подключённых игроков,
  а не все строки `players` (вышедшие больше не занимают слот навсегда).

**REST**

- `GET /api/sessions/by-code/{join_code}` — комната по коду для входа.
- `GET /api/sessions/{id}` не менялся.

**Фронтенд**

- `App.tsx`:
  - вход по коду сначала проверяет комнату через
    `getSessionByCode()`; при неверном коде показывает сообщение и остаётся
    в лобби;
  - `session` берётся из `game_state.session`, поэтому экран ожидания
    появляется у любого вошедшего;
  - подписка на WS одна на всё время жизни приложения (`useEffect`),
    без накопления обработчиков;
  - добавлены баннеры ошибок и уведомлений;
  - добавлены ставка (`set_bet`), «Готов», «Начать игру», «Сбросить карты»;
  - учитывается количество именно подключённых игроков.
- `ws.ts`:
  - фатальные коды закрытия `4000`, `4001`, `4005`, `4006` не вызывают
    бесконечное переподключение;
  - при смене комнаты старый сокет корректно закрывается;
  - причины отказа показываются пользователю;
  - переподключение ограничено 5 попытками.
- `GameTable.tsx`:
  - соперники с очками, ставками, числом карт, статусом сдачи и связи;
  - подсветка того, чей сейчас ход;
  - банк, номер раунда, старшая сила, отметка переигровки;
  - карты на столе с ником владельца и подсветкой лидера;
  - свои карты блокируются, если ход не твой или карта слабее старшей;
  - кнопка «Сбросить карты»;
  - экран результата партии с итоговыми очками и кнопкой «Новая игра».
- `Card.tsx`: добавлены `disabled` и `highlight` (лидер на столе).
- `api.ts`: добавлен `getSessionByCode`.
- `types.ts`: поля `bet`, `folded`, `connected`, `cards_left`, блок
  `session`, `leader_player_id`, `current_power`, `is_tiebreak` и т. д.
- `index.css`: стили баннеров, лобби, стола, карт и экрана результата.
- `index.html`: подключён `favicon.svg` (устранён 404).

## 2. Партия не могла начаться

### Причины

- В `start_round` игроки фильтровались по `score != 0`. В новой комнате
  у всех `score = 0`, поэтому старт всегда падал с `not_enough_funds`.
- В SQLite-базе не было карт: `db_seed_cards.sql` написан под MySQL
  и на SQLite не накатывается.
- Раунд мог зависнуть, если следующему игроку нечем перебить карту.

### Что исправлено

- `app/db.py`: при старте приложения справочник карт заполняется
  52 картами, если таблица `cards` пуста (`build_deck`, `seed_cards`).
- `start_round`: если банкролл ещё не сформирован (все `score = 0`),
  играют все подключённые; фильтр по средствам применяется только после
  появления денег в игре.
- Старт из статуса `finished` обнуляет счёт и ставки прошлой партии
  (кнопка «Новая игра»).
- Повторная раздача без изменения ставки разрешена; повышение банка
  во время партии по-прежнему запрещено (`bank_locked`).
- Ход передаётся только игроку, у которого есть карты. Игроки без средств
  не получают раздачу и не блокируют ход.
- `_finish_if_no_beat()`: если карту некому перебить, раунд закрывается
  и банк забирает владелец старшей карты.
- После сдачи/выхода: если остался один игрок с картами и на столе уже
  есть лидер, раунд закрывается в пользу лидера; если ходов ещё не было,
  оставшийся просто продолжает игру.
- Сдача после завершения раунда возвращает снапшот состояния (no-op),
  а не ошибку — защита от гонок по сети.

## 3. Раздача карт: случайность и колода сессии

### Проблема

На предыдущем шаге раздача была сделана детерминированной
(сортировка по силе + раздача по кругу), чтобы стабилизировать тесты.
Для карточной игры это неправильно: руки всегда повторялись.

### Что сделано

- Новый модуль `app/rooms/deck.py`:
  - `build_session_deck(session_id, db, rng)` собирает колоду из справочника
    `cards`, тасует её через `random.shuffle` и пишет строки в `decks`
    с позициями.
- `POST /api/sessions` создаёт колоду сессии сразу при создании комнаты.
- `start_round` раздаёт карты из `decks` сессии:
  - `PlayerCard.deck_id` ссылается на строку колоды сессии;
  - `card_id` берётся из этой же строки;
  - в первой партии используется колода, созданная вместе с комнатой;
  - при следующей партии колода пересобирается и тасуется заново;
  - остаток колоды остаётся в `decks` (неразданные карты).
- Количество карт на игрока: `min(13, размер колоды // число игроков)`,
  поэтому урезанная тестовая колода не валит старт.
- Тасовка вынесена в `RoomManager(rng=...)`: в проде — случайная,
  в тестах можно передать `random.Random(seed)`.
- Исправлено удаление рук при старте: раньше удалялись несыгранные карты
  **всех** сессий, теперь только текущей.

## 4. Проверка

Выполнено:

- `pytest`: 25 из 26 тестов проходят.
- `npm run build`: сборка и проверка типов без ошибок.
- E2E по WebSocket (два игрока): вход по коду, готовность, старт,
  раздача 13 + 13, ход, сдача, завершение партии.
- Проверка колоды:
  - при создании комнаты в `decks` 52 строки;
  - порядок карт в колоде отличается от исходного (тасовка работает);
  - дублей в колоде нет;
  - после старта у игроков 13 + 13 уникальных карт;
  - все карты входят в колоду сессии;
  - у всех `player_cards` заполнен `deck_id`;
  - две разные комнаты получают разные руки.
- Проверка в браузере двумя вкладками: второй игрок видит комнату,
  оба видят друг друга, получают по 13 карт, ход и сдача обновляют
  оба экрана, показывается результат партии.

### Известное ограничение

`tests/test_rules.py::test_tie_causes_replay` остаётся красным. Тест
требует, чтобы при раздаче по одной карте второй игрок успел сходить
после первого, хотя остальные тесты требуют закрывать раунд, когда
у игрока закончились карты. Эти ожидания противоречат друг другу;
тест не изменялся. Логика переигровки при равных картах в
`_resolve_round` сохранена.

## 6. Запуск

```bash
# бэкенд
python -m uvicorn app.main:app --reload --port 8000

# фронтенд
cd frontend
npm run dev

# тесты
python -m pytest tests/ -v
```

Колода и карты создаются автоматически: справочник заполняется при старте,
колода комнаты — при `POST /api/sessions`.
